# Vismaz — Craft CMS 5 Plugin

## Project Overview

Vismaz connects Craft Commerce 5 to **Visma eAccounting** — the product sold in Sweden as *Visma
eEkonomi*, renamed *Bokföring & Fakturering* under the **Spiris** brand in 2025 (the API did not
change with the rebrand). Distributed as `justinholtweb/craft-vismaz`. **Lite $79 / Pro $149.**

## Why it exists

Posting an order to an accounting API is the easy part. Vismaz's value is entirely in the Swedish
domain rules that generic integrations get wrong: öresavrundning as a real posting to 3740,
omvänd betalningsskyldighet against a VIES-validated VAT number, OSS destination rates with a
per-country quarterly report, and per-gateway settlement accounts with the processor's fee booked
as its own cost. Plus SIE 4 export, because a large share of Swedish merchants run desktop *Visma
Administration*, which has no public API.

## Tech Stack

- **PHP 8.2+**, **Craft CMS 5.3+**, **Craft Commerce 5.0+**, Yii2, Twig
- No build step: no asset bundles, no JS beyond inline `{% js %}` blocks

## Architecture

- Namespace `justinholtweb\vismaz`, package `justinholtweb/craft-vismaz`, handle `vismaz`

### The three invariants

1. **`services\Documents` is the only place a Commerce order becomes Visma data.** The CP preview,
   the console dry run, the real push and the SIE writer all consume the same `models\Document`.
   A preview generated by different code from the push is a preview nobody can trust.
2. **`services\Sync::record()` is the only place a document row is written.** Idempotency, the
   attempt counter and the sent/failed transition are decided once and cannot disagree.
3. **`services\Tax::treat()` is the only place a VAT treatment is decided.** Invoice rows, voucher
   lines, the SIE file and the OSS report all ask it, so a sale cannot be reverse-charged on the
   invoice and domestic in the quarterly report.

### Data model

- `{{%vismaz_documents}}` — unique on `(type, sourceKey)`; **that index is the idempotency
  guarantee.** Keys are `order:<id>`, `refund:<id>:<hash>`, `voucher:<start>:<end>`.
- `{{%vismaz_documentorders}}` — unique on `orderId`, so an order cannot land in two vouchers.
- `{{%vismaz_entities}}` — Craft/Commerce identity → Visma GUID, with a content hash so an
  unchanged customer is not re-pushed on every order.
- `{{%vismaz_tokens}}` — one row per environment, so sandbox and production coexist.
- `{{%vismaz_log}}` — the connection log.

### Dispositions

- **Fails open.** Order completion queues a job; nothing calls Visma inline. A Visma outage must
  never stop a customer paying.
- **When in doubt, charge the VAT.** A VAT number VIES cannot confirm — wrong, or VIES is down —
  leaves the sale taxed. Zero-rating on a timeout is the merchant's liability.
- **Balance is checked before sending.** Visma rejects an unbalanced voucher without saying which
  line is wrong, so `Document::balances()` catches it first and names the difference.
- **Retries rebuild, they do not replay.** `Sync::rebuild()` re-derives the document from the
  order as it is now; an order corrected after a failure pushes as corrected.
- **Never trust the mapping — reconcile.** `Sync::reconcile()` compares the total Visma booked
  with the total that was sent; a disagreement marks the document `mismatched` rather than `sent`.
  A subtly wrong mapping does not throw, it books the wrong number, and nobody notices until a
  bank reconciliation months later. Every plugin in this family does this.
- **Tokens are encrypted at rest.** A Visma refresh token is good for two years.

## Protocol notes (read, not guessed)

- Auth: authorization code. `identity.vismaonline.com/connect/{authorize,token,revocation}`,
  client credentials as **HTTP Basic** on the token call. Scopes `ea:api ea:sales ea:accounting
  offline_access` — **without `offline_access` there is no refresh token at all** and the
  connection dies an hour after it is made. `prompt=select_account` is required in practice:
  Visma otherwise reuses the last company silently.
- **Access token 60 minutes. Refresh token two years, but dead the moment the user changes their
  password.** The refresh token **rotates** on every use, hence the mutex around refreshing.
- **Sandbox is a different host in both places**: `identity-sandbox.test.vismaonline.com` and
  `eaccountingapi-sandbox.test.vismaonline.com/v2`.
- **Rate limit 600/minute per client per endpoint**, `429` with application `ErrorCode: 4010` and
  a "try again in N seconds" message — the useful number is in the message, not `Retry-After`.
- JSON is **PascalCase**; list endpoints answer `{Meta, Data}` and page with OData `$top`/`$skip`.
  Reading `Data` once and stopping silently truncates the answer.
- VIES: `https://ec.europa.eu/taxation_customs/vies/rest-api/ms/{country}/vat/{number}`, no key.
  **Greece's VAT prefix is `EL`, not its ISO code `GR`** — `Vies::parse()` owns that translation.

## BAS accounts — verified, and two pairs are counter-intuitive

Checked against the published chart rather than recalled, because a wrong account number does not
fail loudly, it quietly misfiles a year of revenue.

- **`3305` is services sold *outside* the EU; `3308` is services to another EU country.** This is
  the reverse of the obvious guess.
- **`3520` is invoiced *freight*; `3540` is the invoicing fee.** Also easy to swap.
- `3001/3002/3003/3004` domestic 25/12/6/0 %, `3105` goods outside EU, `3106/3108` goods to the
  EU taxable/exempt, `3740` öres- och kronutjämning, `1510` receivables, `1580` card receivables,
  `2610/2620/2630` output VAT, `2614/2624/2634` reverse-charge output VAT (**those are for
  purchases under reverse charge — a reverse-charged *sale* has no output VAT posting at all**),
  `6570` bank charges.

## Traps found while building this

- **`getAdjustmentsTotalByType()` is not public in Commerce 5** — on `LineItem` it is private
  (`_getAdjustmentsTotalByType`) and on `Order` it does not exist. The public accessors are
  `LineItem::getTax()`, `getTaxIncluded()`, `getDiscount()`, `getShippingCost()` and
  `Order::getTotalTax()`, `getTotalTaxIncluded()`, `getTotalDiscount()`, `getTotalShippingCost()`.
  Calling the old name throws `UnknownMethodException` at runtime, not at lint.
- **PHP's `+` on arrays keeps the left operand's keys.** `$defaults + ['error' => $message]` where
  `$defaults` already has `error => null` silently discards the message. Bit me in `Vies::check()`.
- **Float VAT rates drift.** Commerce arithmetic really does produce `24.999999999999996`, which
  without `Bas::normaliseRate()` books to the *exempt* account. Every total in the plugin is
  summed in öre (`Money`) for the same reason.
- **A SIE file is CP437, not UTF-8.** `#FORMAT PC8` is a promise about the bytes; Å/Ä/Ö sent as
  UTF-8 make importers reject the file or mangle every account name in the chart.
- **A treatment must always explain itself.** An EU sale where Commerce charged no tax fell
  through every branch of `Tax::treat()` and came out with an empty `reason`. It now lands as
  `exempt` with an explicit "check the tax setup" message — a silent zero-rate is precisely what
  surfaces at an audit.
- **Commerce refuses an address element it does not own.** Pass an *array* of attributes and let
  Commerce build the owned element.
- **`Security::encryptByKey()` returns raw binary.** Writing it straight into a `text` column on
  a utf8mb4 connection fails with `SQLSTATE[22007] Invalid datetime format: 1366 Incorrect string
  value` — an error naming a *datetime* problem for a *token* column. Base64 both ways.
- **`/Users/jholt/Sites` is itself an uncommitted git repo**, so `git add -A` from a plugin folder
  without its own `.git` stages the whole Sites directory. `git init` the plugin first.
- **Never mark plugin settings `required`** — Craft validates them wholesale, so one required
  credential blocks saving every other setting on a fresh install.
- **Never nest a `<form>` in a CP template** — post secondary actions with `Craft.sendActionRequest`.
- **Project config writes are buffered** until the request ends; a bare console script has to
  flush them itself.

Vismaz is part of the Commerce-to-accounting family: `[[project_craft_knox]]` (Fortnox, the other
Swedish one — read `[[craft-knox-gotchas]]` first, it shares the öresavrundning problem),
`[[project_craft_econz]]` (e-conomic, also Visma-owned, DK), `[[project_craft_sevvies]]` (sevDesk,
DE), `[[project_craft_datevz]]` (DATEV, DE) and `[[project_craft_holding]]` (Holded, ES). They all
reconcile against the order total rather than trusting the mapping. See `[[craft-plugin-gotchas]]`
for family-wide traps and `[[project_craft_shipper]]` for the Commerce conventions.

## Testing

No local PHP on this Mac. Everything runs inside the plugin-testing container:

```sh
cd ~/Sites/plugin-testing
ddev exec php /var/www/craft-vismaz/tests/integration/checks.php   # 171 checks
ddev exec bash -c 'find /var/www/craft-vismaz/src -name "*.php" -print0 | xargs -0 -n1 php -l'
```

The suite switches to Pro for the bulk of the run, exercises Lite in its own section, and restores
the edition, the settings and every fixture in a `finally`. Nothing in it talks to Visma —
correctness lives in the builders and the tax decisions, not in the transport.

**Harness notes** (neither is a Vismaz bug):
- `craft-penny` types its `Elements::EVENT_BEFORE_SAVE_ELEMENT` handler as `ModelEvent` while
  Craft passes an `ElementEvent`, so every element save fatals while it is enabled. `checks.php`
  detaches that handler in-process (never persisted) so fixtures can be created.
- `craft-bexy`'s `console\controllers\MetaController::table()` is declared non-public while
  `craft\console\Controller::table()` is public, which fatals **`craft help`** for the whole
  harness. Vismaz's own commands run fine when addressed directly.

- `Craft::t('vismaz', '…')` for user-facing strings; `src/translations/{en,sv}/vismaz.php`
